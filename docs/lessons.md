# 歷史教訓（與程式中的落實機制對照）

這五條教訓是系統設計的硬約束。任何改動若違反其中一條，先回來讀這份文件。

## 1. 幾何座標一律來自建檔資料，禁止臨場猜測

新點位必須人工確認座標與視線方位後才入庫（`data/viewpoints.json`）。

**程式落實**：`geometry.load_viewpoints()` 是唯一的座標來源；`solar` / `analysis`
所有幾何計算只吃 `Viewpoint` dataclass，程式中沒有任何硬編碼座標。
測試以實測驗證值鎖定種子資料（劍潭山→觀音山 255°/11.1km）。

**全台化的座標政策（v1.2.x，維護者核定）**：點位座標以**可信公開資料交叉查證**
（官方觀光資訊、OpenStreetMap、維基百科等，出處記於 `coord_source`）即可入庫，
不要求實地確認——「禁止臨場猜測」禁的是憑空編造，不是禁止查證好的公開資料。
但**遮蔽幾何仍不得臆造**：`horizon_obstruction` 沒有實測就留空、
`open_azimuth_range` 取寬鬆西向，寧可少算遮蔽也不假裝知道。
`needs_field_verification` 旗標保留給未來座標存疑的新提案點使用。

## 2. 「多雲」不代表會燒 —— 分層雲量驅動

低雲（<2000m）擋太陽；只有中高雲會被日落點燃。總雲量僅作參考顯示。

**程式落實**：`weather.WeatherWindow` 強制取得 `cloud_cover_low / mid / high`
三層雲量（任一層缺值即降級為「資料不足」）；`scoring.score()` 的所有規則
以 `cloud_low` 與 `mid_high = max(cloud_mid, cloud_high)` 為輸入，
`cloud_total` 不參與評分。

## 3. 「穩定炎熱天照樣能燒」—— 防過度悲觀條款（5/25 教訓）

即使高溫穩定、無鋒面，只要高雲存在就有燒的可能。

**程式落實**：`scoring.py` 防過度悲觀條款 —— `cloud_high ≥ 20` 時
C+D 合計不得低於 15%（常數 `ANTI_PESSIMISM_HIGH_MIN` / `ANTI_PESSIMISM_CD_FLOOR`），
在所有規則（含死亡條款）之後最後套用。

## 4. 火燒雲常連日出現 —— 持續性加成

昨天有燒，今天燒的機率明顯升高（24–48h 持續性）。

**程式落實**：`scoring` 的 `burned_yesterday` 加成 +15（作用於 C+D）。
資料來源是 `logbook.burned_on()` 讀 `outcomes.csv` 中**昨日的實際回報**
（C 或 D 才算有燒）——不是昨天的預測。沒有回報就沒有加成，
所以每天 19:15 的 `/report` 回報很重要。

## 5. 早上的預報對午後對流幾乎無鑑別力

台北夏季午後對流是預報最大的雜訊來源，早上的模式輸出無法分辨。

**程式落實**：
- 16:20 判定（`push-daily`）一律在執行當下重新打 API，用最新一次預報資料。
- 中午前查詢（或查詢未來日期）時，`analysis` 標記 `preliminary=True`，
  訊息附註「初步展望，信心低，以當日 16:20 推播為準」。
- 校準時只用「當日最後一次 16:20 前後的預測」對 outcome（見 logbook 註解）。

## 6. 「看到太陽本身」與「天空色彩」是兩個獨立軸（來自使用者實地回報）

實地回報：清晨晴朗、傍晚西邊一條低雲帶擋住日輪，**看不到太陽本身**，
但天空上方**一整片橘色**（非火燒）。舊分類把「看得到太陽下山」綁進 B，
使這種常見情境無家可歸（使用者形容「介於 A、B 之間」）。

**真相**：日落的觀感至少有兩個獨立維度——
1. **天空色彩／戲劇性**（灰暗→橘色霞光→局部火燒→全面火燒）：由中高雲當燃料主導。
2. **日輪可見度**（看得到／被低雲擋住）：由低雲那條帶主導。

低雲高 → 擋住太陽本身，但上方中高雲仍可能被點亮 → 「看不到太陽、卻滿天橘色」。

**程式落實（v1.3.0，語意釐清、機率數值不變）**：
- A–D 重定義為**純天空色彩**：A 灰暗無色、B 橘色天空/霞光（不論看不看得到太陽）、
  C 局部火燒、D 全面火燒。`sunset_visible`(B+C+D) 改稱「有夕陽色彩」而非「看得到太陽」。
- 低雲干擾區間（30–70）新增理由：`scoring.DISK_SKY_FUEL_MIN`——
  「太陽本身可能被低雲擋住，但上方中高雲仍可能被點亮」，PWA 白話摘要同步呈現。
- 回報表單新增選填「太陽本身」欄（看得到／被擋住），ingest 以 note 標記存下，
  **不併入 A–D 共識**（維持校準標籤單純）。

## 7. 排程「準時」是假設，不是事實：遲到的預測會變成偷看答案（2026-10 健檢）

2026-07～10 實測：GitHub Actions 的 `schedule` 觸發中位數晚 **2.9 小時**，近期常晚
**5–8 小時**（89 次中 69 次晚超過 1.5 小時）。「16:20 日落預測」實際多在 21:00–01:00
才跑——日落早已發生，Open-Meteo 回給的「17–19 時預報」其實已是同化過觀測的分析值。
結果：616 列預測中 **60% 在日落後才發出**，69 天裡只有 17 天有真正事前的預測。
這種資料拿去校準，模型會看起來比實際準，比沒資料更糟。

**程式落實**：
- `sunset/leadtime.py`：距該點日落 ≥ 60 分鐘發出才算有效預測。
- 寫入端拒寫逾時預測；讀取端（週報、app）忽略既有逾時列——append-only 日誌不改寫，
  原始列保留可稽核。Python 與 JS 兩邊過濾逐列一致（實測 616 列完全相同）。
- 觸發太晚 → 自動改預測**明天**；一天排 4 個 GitHub 時段＋去重（90 分鐘內已有同日
  有效預測就略過），推播只在首推／判定改變時送、夜間不推。
- 準點主觸發交給 Cloudflare Worker cron（`scheduled()` → workflow_dispatch）。

**教訓**：凡是「point-in-time」紀錄，都要能從紀錄本身驗證時間點（發布時間 vs 事件時間），
並在讀取端強制檢查——不要信任排程器的準時性。

## 8. 同步不能 force-push：公開 repo 會自己長出 commit（2026-10 健檢）

`sync-public` 原本用 `git push --force` 把 dev 分支蓋到公開 repo 的 main。但公開 repo
每天有 bot 日誌 commit，也會直接合併 PR（2026-09 的 Airflow 編排層）。force-push 把
這些全部抹掉——2026-07 的同步就讓 `predictions.csv` 的早期紀錄消失。

**程式落實**：改為「先 merge 公開 main、再一般快轉 push」，衝突就整個失敗不推；
只在 dev repo 執行。dev 端每次開工前先把公開 main 快轉進來。

**教訓**：append-only 是整條鏈的性質，不只是寫檔函式的性質——任何會覆寫歷史的
操作（force-push、rebase 已推送分支、重建檔案）都會破壞它。

## 附：資料來源紀律

- 禁止爬任何天氣網頁 HTML（歷史教訓：Yahoo 氣象網頁回傳過期快取），
  一律走結構化 API（Open-Meteo 主力、CWA 開放資料交叉驗證）。
- 所有 fetch 加 timeout、重試一次，失敗時降級輸出「資料不足」而非崩潰。
- 預測日誌 append-only、point-in-time：寫入後永不修改，
  任何規則常數變動都要 bump `ENGINE_VERSION`。
